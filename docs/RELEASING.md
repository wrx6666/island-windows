# Как выпустить обновление

## Автоматически при изменении версии

1. Внеси изменения в исходники.
2. В `release-version.txt` увеличь версию, например с `0.11.0` до `0.11.1`.
3. Сделай commit и push в `main`.

GitHub Actions проверит исходники и расширение, соберёт установщик и опубликует релиз с файлами обновления. Изменение только исходников без изменения `release-version.txt` запускает проверки, но не публикует новую версию.

## Вручную через GitHub Actions

1. Загрузи изменения исходников в ветку `main`.
2. Открой **Actions → Build Island release → Run workflow**.
3. Укажи новую версию из трёх чисел, например `0.11.1`. Номер должен быть выше опубликованного.
4. Дождись успешной сборки. Workflow опубликует новую версию в **Releases**. При необходимости допиши заметки к выпущенной версии.

После публикации приложения с адресом этого репозитория увидят обновление при следующей проверке. Вручную можно проверить сразу через настройки Island. Никакие персональные токены в приложении или исходниках не нужны: для выпуска workflow использует временный `GITHUB_TOKEN` с правом `contents: write`.

## Какие файлы нужны в релизе

| Файл | Назначение |
| --- | --- |
| `IslandSetup.exe` | Один файл для установки на другом ПК |
| `Island.Desktop-<версия>-full.nupkg` | Полный пакет обновления |
| `releases.win.json` | Каталог версий и контрольных сумм для обновлятора |
| `assets.win.json`, `RELEASES` | Дополнительные метаданные Velopack |
| `*.sha256` | Контрольные суммы публикуемых файлов |
| `Island.Desktop-win-Portable.zip` | Дополнительная переносимая сборка |

Workflow загружает комплект автоматически. Одного Setup.exe для встроенной проверки обновлений недостаточно: не удаляй `.nupkg` и `releases.win.json` из опубликованного релиза. Не меняй `packId` (`Island.Desktop`) между версиями и не перезаписывай уже опубликованные версии.

## Локальная сборка

```powershell
pwsh ./build-installer.ps1 -Version 0.11.1 -GitHubRepository "https://github.com/wrx6666/island-windows"
```

Файлы появятся в `release/modern`; загрузи их в один обычный GitHub Release с тегом `v0.11.1`. Адрес репозитория встраивается при сборке. После переноса репозитория установкам со старым адресом может потребоваться переходная версия.

## Что не загружать в исходники

Личные настройки, музыкальную историю, профили браузера, логи, `.tools`, `bin`, `obj`, `artifacts` и готовые установщики. Исходники идут в Git, установщики и пакеты — в Releases. Публичная история репозитория начинается с подготовленной копии проекта без локальной истории разработки.
